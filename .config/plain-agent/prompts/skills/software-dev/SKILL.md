# Software Dev

## Principals

人間がソフトウェアを開発・メンテナンスする際の認知コストを抑える：
- 抽象度で整理する：実装の話はコードコメント、仕様・設計はドキュメント。抽象度レベルを混在させない。
- 情報量を抑える：読み手が判断・行動をするのに必要な情報だけを書く。
- 重複を避ける：コードで表現できるものは、コードをSingle Source of Truthとする。同じ情報をドキュメントに書かない。

## Workflow

※ 以降の `docs#X` は、特定のファイルではなくプロジェクトのドキュメント内の該当セクションを指す。
ドキュメントの格納先はユーザーと相談して決定する。

### Understand

解決すべき問題、制約を理解するために、ユーザーとの議論やコードベースの調査を行う

Output:
- docs#Purpose（存在意義）
- .work/<feat-name>-research.md

Review:
- 問題と制約が明確か
- 既存の周辺システムを説明可能か

### Define Spec

外から見たシステムの振る舞いを定義する

Output:
- docs#Behavior（ユースケース、外から見た振る舞い）

Review:
- 問題を解決するためのユースケースの漏れや無駄はないか
- 検証可能な振る舞いとして定義されてるか
- 実装の詳細が書かれていないか

### Design

システムを実現するためのアーキテクチャを設計する

Output:
- .work/<feat-name>-research.md (既存のソリューションや、利用可能な技術を調査)
- docs#Architecture（主要な構成要素、責任境界、ワークフロー、ER Overview、状態遷移）
- docs#Operations（デプロイ、設定などの運用方法）
- docs#Decisions（非自明な設計判断）
- docs#Limitations（既知の制約）
- Code/外部から見たインターフェース + READMEからの参照
- Code/データモデル + READMEからの参照

Review:
- ユースケースをサポートしているか
- 正常系、異常系の考慮漏れはないか
- パッチワーク的な作りになってないか（異常系の存在を消す根本的改善はできないか）
- 構成要素や機能名称の役割が明確な名前になっているか
- 全体整合性が取れているか
- 過剰な抽象化がないか
- 技術文書で使用される自然な言葉・表現か

### Plan

実行可能なタスクに分解する

Output:
- .work/<feat-name>-tasks.md

Review:
- 作るべき構成要素が網羅されているか
- 人間がレビュー、検証しやすい粒度、順序か

### Implement

人間がレビュー可能な粒度で実装する

Output:
- Code（Testsで検証済みの状態）
- Tests（詳細レベルの振る舞いを説明）

Review:
- 命名:
  - 関数や変数の役割が明確な名前になっているか
  - 名前空間に対して一般的すぎないか
- コメント:
  - 公開API・関数のコメントは、コードを読まずに正しく呼び出すための情報を過不足なく書いているか
  - コードから自明なコメントがないか
  - 技術文書で使用される自然な言葉・表現か
- テスト:
  - 実装の詳細ではなく、振る舞いを検証しているか
  - 境界値をテストしているか
  - ケースの漏れ、ダブりはないか・同値クラスとして整理できないか
  - セットアップ、実行、検証の区切りが明確か（given/when/thenなどのコメント）
  - 結果が実行順に依存しないか
  - 実行速度に改善余地はないか
- セキュリティ:
  - 認証・認可チェックを実施しているか
  - 権限が最小化されているか
  - 外部入力を検証、サニタイズしているか
  - SQL, OSコマンドなどのインジェクション経路はないか
  - 機密情報、個人情報がコード、ログ、レスポンスに露出する経路はないか
  - 機密情報を暗号化しているか
  - ライブラリやコンテナイメージのバージョンがピン留めされているか
- エラーハンドリング: 
  - 発生しうるエラーを処理しているか
  - エラーをサイレントに握り潰してないか
  - リトライ上限、バックオフが定義されているか
  - 冪等性が考慮されているか
  - タイムアウト、部分成功、同時・重複実行時の挙動が定義されているか
  - ロールバック、回復処理が必要なイベントを放置してないか
- 互換性:
  - 外部から見たインターフェース・振る舞いに破壊的変更がある場合、それは意図されたものか
  - デプロイ中に、新旧のバージョンが混在しても動作するか
- 性能: 
  - 外部IO、計算量、メモリ使用量が肥大化するポイントはないか
- 観測性: 
  - 主要な処理の開始、成功、失敗をログで追跡できるか
  - エラー原因、対象を調査する情報があるか
  - エラー率、レイテンシ、処理量などの指標を取得できるか
  - request id, trace idなどで処理を追跡できるか
  - 機密情報、個人情報をログに出してないか
- 組織ルール準拠:
  - ログの保管期間
  - 暗号化 (CMK要否)

### Tidy Up

恒久的に残すものを整理する

Output:
- 整理されたドキュメント（重複削除、Codeで説明可能な詳細を削除、陳腐化した情報の削除）
- 整理されたCode（自明・冗長なコメントの削除）
- 整理されたTests（同値クラスの重複削除）
- 整合性の取れたドキュメント、Code、Tests（内容の整合性、重複する情報を整理）
- .work/ 配下の一時ファイル削除（全タスク完了後）

## Appendix

### ドキュメント構成

プロジェクトルール、ユーザーからの指示がない場合の構成

- README.md: Purpose, 各ドキュメントへのリンク
- docs/
  - behavior.md (Behavior, Limitations)
  - architecture.md
  - operations.md
  - decisions.md

### 非機能系のデフォルト

指示がない場合は以下をユーザに提案する

Logging (Daemon application):
- 構造化出力はstdout、構造化不可能な出力はstderr
- 構造化フォーマット: `{ "event": "<一意なイベント種別>", ... }`
  - ログレベルのキー (level, severity) はプラットフォームに合わせる
- trace idなどのコンテキストは自動で含める (Node.jsであればAsyncLocalStorageを利用)

Dependency Injection:
ライブラリ、フレームワークは利用せず、コンストラクタや関数の引数から依存を明示的に注入する構造を採用
`foo(deps: {...}, input1, input2, ...)`

Test Runner:
言語・ランタイムが標準で備えていればそれを採用

### レビューの戦略

- バイアスやノイズを減らすためにコンテキストを整理する (compact_context)
- 漏れがないようにレビューの観点ごとにサブエージェントに任せる
- 設計・実装のレビューは software-architect に任せる
